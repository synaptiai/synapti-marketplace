# Decision Journal — Issue #269

**Title**: feat(flow): a quality run that executed zero tests or skipped every test is not recorded as passing
**Epic**: #258
**Branch**: feature/issue-269-quality-run-s1
**Created**: 2026-10-01

## Summary

After a Bash call that Flow already records as a passing built-in test run, `hooks/scripts/record-quality-run.sh` can ask System One (site `quality.tests-ran`) whether the output shows at least one test actually executing. With the site `on`, a confident `none_ran` or `all_skipped` answer records the run as not passing, with that reason, and the task-completion gate names it. The site ships `off`. Off, no provider, or no answer: System One adds nothing to the ledger entry and changes nothing at the gate, and Bash calls that are not passing built-in test runs start nothing for it and make no request.

This change also changes how the hook derives a run's exit code, for every user, whatever the site's mode, including off. Claude Code sends no exit code for a Bash call that succeeds, so before this change every passing run was recorded with no exit code and never counted as passing. Now a call that finished in the foreground is recorded as exit 0 when the test command is the whole command or follows only plain prefixes, and any other shape is recorded with no exit code. With the site off, the ledger entry and the gate therefore differ from before in the exit code alone (see "Acceptance criterion 6" below).

## Specification

### Non-goals

- Recognizing runners missing from the built-in list (`uv run pytest`, `./gradlew test`, `tox`). System One may only add caution, so it cannot create passing records; extending the list is a deterministic pattern change for another issue.
- Judging lint, typecheck, build, or the `project` kinds (the built-in `verify.sh`/`check.sh` pattern and `testing.qualityCommandPatterns`). Only `kind=test` from the built-in list is asked.
- Upgrading anything. A PostToolUseFailure payload, a non-zero or null exit code (as derived below), a masked command or an interrupted call never reaches the ask.
- Telling Claude at PostToolUse time. The hook still always exits 0 with empty stdout; the reason reaches Claude through the TaskCompleted gate message.
- Changing the gate beyond reading the new field and wording the message for a run with an unknown exit code: dirty/clean rules, digest, and block/warn/off are unchanged.
- Storing test output anywhere new. The client records only the state's sha256; the ledger keeps the command's first 200 characters, as before.
- A deterministic keyword or regex reading of the output, as fallback or replacement.
- Python older than 3.12.
- Tying the exit-code rule to the site. The rule applies to every user whatever the site's mode; the site only adds `s1_state_sha256` and `output_check`.
- Accepting `env`, `time`, `nice` or `timeout` as prefixes. Each passes the test command's status on, but the rule stays the user's simple one: the listed prefixes only, so a run behind one of these records no exit code and the gate names these prefixes.

### Acceptance criterion 6

"With the decision point off, no provider configured, or no answer, behavior is identical to today's" is read as: the System One part adds nothing to the ledger entry or the gate in those cases. The exit-code rule above is part of this change by the user's decision and applies whatever the site's mode, so with the site off a finished plain test run is recorded with exit code 0 where it was recorded with none before, and it can pass the gate. The off and no-answer scenarios compare every other field with the line the hook at the base commit writes, and check the exit code on its own.

### Failure modes

| Condition | Behavior |
|---|---|
| Timeout (`timeoutMs`, default 3000, clamped 200-30000) | flow-s1.sh exits 3; the entry is appended unchanged and stays passing. At `timeoutMs` 60000, clamped to 30000, with a reply held 40 s, the hook returns in 29 to 38 s with the entry appended. Claude Code's default command-hook timeout is 600 s for PostToolUse ("Defaults: 600 for `command`, `http`, and `mcp_tool`", lowered only for UserPromptSubmit, PreModelSwitch, PostModelSwitch, MessageDisplay and SessionEnd; code.claude.com/docs/en/hooks, read 2026-10-01), well above 30 s plus overhead, so hooks.json needs no explicit `timeout`. |
| HTTP error, connection failure, redirect, malformed reply, abstention, missing answer, below threshold | exit 3; entry unchanged; the client still writes a record with the reason. |
| Provider none (the default) | The mode comes from `bin/flow-s1-mode.sh quality.tests-ran`, which prints nothing without a configured provider, whatever the mode: the hook runs only that mode check, starts no client, writes no record and stamps no `s1_state_sha256`. Entry otherwise unchanged. |
| `settings-refused` (plugin inside the repository) | No answer; the run stays passing. |
| Repository sets `shadow` or `on` above the user's mode | The hook takes the mode from `bin/flow-s1-mode.sh`, which uses the lower of the user's mode and the repository's (`off` when the user's is unset or no provider is configured), so after the mode check no client starts and no digest is stamped. |
| Missing stdout/stderr in tool_response | Empty lists; still asked. Non-UTF-8 bytes are replaced by jq when the payload is read. |
| mktemp fails, the state cannot be written, or no sha256 tool | The ask is skipped and the entry is appended as before. Every step that can fail is checked with `||`, never inside a `$(...)` whose failure could exit the hook before the append. |
| No jq, no session_id, no ledger helper | Exit 0 before the ask, as before. No python3/PyYAML gives `python-missing`; a missing questions entry gives `unknown-site`; both leave the entry unchanged. |
| Exit 0 with a choice outside {none_ran, all_skipped}, or stdout jq cannot parse | Entry unchanged. A parse failure never downgrades. |
| Record written, ledger append fails | The ledger fails as before (`|| true`); the orphaned record has no ledger line with its sha256 and drops out of the comparison. |
| One tool_use_id fires PostToolUse and PostToolUseFailure | Only the PostToolUse branch asks; the ledger keeps the first append. |
| Hook stopped (SIGINT, SIGTERM, SIGHUP) while the client waits | A trap removes the state file once the client exits; the hook then appends the entry without `s1_state_sha256` or `output_check` and exits 0. |
| Hook killed (SIGKILL) while the client waits | The state file stays in TMPDIR; the next ask removes this user's `flow-s1-quality.*` files there that are older than 10 minutes. |
| Test run after `cd <dir> &&` into another repository, or into a directory that cannot be entered now | Not asked: the mode was read for the session's repository, and the other repository's settings may turn the site off. The entry is recorded as without System One. |
| Client stops before writing a record (no python3, settings it refuses) or cannot write it | The entry carries no `s1_state_sha256`, since no record holds that state. |

### Interface contracts

- **Exit code** (record-quality-run.sh, computed once and used by the pre-filter, the state and the ledger entry, for every user whatever the site's mode): 130 when `tool_response.interrupted` or `is_interrupt` is true; else null when `tool_input.run_in_background` is true; else `tool_response.exit_code` when it is a number; else, on a failure payload, the N of the leading `Exit code N` of `error`/`tool_error`; else, when `hook_event_name == "PostToolUse"`, `tool_response` is an object, `tool_response.interrupted` is false and every key of `tool_response` is one a finished foreground call carries (`interrupted`, `isImage`, `noOutputExpected`, `stdout`, `stderr`, `bashEditDiff`, `gitOperation`, `staleReadFileStateHint`, `persistedOutputPath`, `persistedOutputSize`), 0; else null. Any other key, known (`backgroundTaskId`, `backgroundCwdHint`, `backgroundedToDeliverMessage`, `timedOutAfterMs`, `returnCodeInterpretation`) or not, records null. A 0 (from either source) is kept only when the matched command is the whole command, or follows nothing but `cd <dir> &&` prefixes, variable assignments such as `FOO=1` (where the directory and the value may hold only letters, digits and `. _ / ~ + - : @ % , =` (a leading `~` only in the directory), and only space and tab separate the words; any other character could change how the rest of the line is read), and one leading line holding only `set` with the options `-e`, `-u`, `-x`, `-v` and `-o pipefail`, `errexit`, `nounset` or `xtrace` (`set -euo pipefail`; `set -n` or `set -o noexec` would read the command without running it); redirections such as `2>&1`, `> file` and `&> file` are allowed. Every other shape records null: a pipe, `;`, `&&` or `||` after the matched command, a subshell, group, command substitution or process substitution, a heredoc or here-string anywhere in the command, a background `&`, a command over more than one line apart from that leading `set` line, and the prefixes `env`, `time`, `nice` and `timeout`. Claude Code reports one status for the whole call, and these shapes are the ones where that status can only be the matched command's. The check reads the command as written, quotes included, with one pattern match per step, so the hook takes at most about half a second longer on a 50 KB command than on a short one (macOS, bash 3.2 in a UTF-8 locale, measured 2026-10-02), and a `|` or `;` inside a quoted argument also gives null. A built-in pattern must match at the start of the remaining simple command. For a repository pattern, its leftmost match there must be non-empty and start the command, so an unanchored pattern after `echo` gives null; a pattern bash cannot compile gives null. A masked run (`|| true`) therefore records null. Null never passes; the gate says the exit code is not known, names a timeout, a call in the background and the refused prefixes `env`, `time`, `nice` and `timeout` among the causes, and asks for the test command to be run on its own. Claude Code sends no `exit_code` for Bash: in this machine's Claude Code 2.1.270 to 2.1.283 transcripts (read 2026-10-07), every Bash result carries `interrupted`, `isImage`, `noOutputExpected`, `stdout` and `stderr`; finished foreground calls add only `bashEditDiff`, `gitOperation`, `staleReadFileStateHint`, `persistedOutputPath` and `persistedOutputSize`; `backgroundTaskId`, `backgroundCwdHint`, `backgroundedToDeliverMessage`, `timedOutAfterMs` and `returnCodeInterpretation` appear only on calls moved to the background, timed out, or read as informational. The user's real ledgers on 2026-10-01 held 9,099 PostToolUse quality runs, all with a null exit code, and 123 PostToolUseFailure runs, 101 of them with the exit code read from `error`. `returnCodeInterpretation` marks a non-zero exit that Claude Code delivered as PostToolUse because it reads it as informational (seen: "No matches found", "Files differ"). These keys come from the transcript's record of the tool result, not from a captured hook payload.
- **Pre-filter** (record-quality-run.sh): ask only when `hook_event_name == "PostToolUse"`, KIND is `test` from the built-in list, the exit code above is 0, MASKED=false, FAILED=false, and the effective mode for `quality.tests-ran` is `shadow` or `on`. The mode comes from `bin/flow-s1-mode.sh quality.tests-ran`, the one place that applies the mode rule: the lower of the user's mode (user settings or the plugin default) and the repository's, `on` > `shadow` > `off`, and nothing printed (off) without a configured provider.
- **State** (JSON, built by the hook with one `jq -c`): `{"command": <first 2000 chars, with the value of each assignment in the leading prefixes replaced by `***`>, "exit_code": <the exit code above, always 0 here>, "output_head": [first 40 stdout lines], "output_tail": [last 200 stdout lines], "stderr_tail": [last 40 stderr lines]}`, each line cut to 400 characters, one trailing newline removed before splitting. Lines, not one string, because the client shortens a too-long state by cutting each string from its end, which keeps every line, including the runner's summary at the end.
- **Client call**: `flow-s1.sh ask --site quality.tests-ran --state-file <mktemp> --state-format json --current pass --ref <ref>`, no `--run-id`, stdout and stderr captured, stderr discarded. The temporary file is removed whatever the exit status, and by a trap if the hook is stopped (INT, TERM, HUP) while the client runs; the hook then records the run without the answer. Asked only when every `cd <dir>` in the prefix, followed from the payload's cwd, ends inside that cwd's git repository.
- **Ref** (not in the spec; the foundation PR made `--ref` required for every call site): `quality-run:<tool_use_id>` when the tool_use_id matches the client's ref shape (`[A-Za-z0-9][A-Za-z0-9._:/#@+-]*`, at most 200 characters with the prefix); otherwise `quality-run:session:<session_id>` under the same check; otherwise `quality-run:unknown`. A ref the client would refuse would end the call as a usage error with no record, so the hook never passes one.
- **Ledger entry additions**: when the hook called flow-s1.sh and the client wrote a record for the state (its sha256 is among the last 200 lines of the records file): `"s1_state_sha256": "<sha256 of the state file bytes>"` (the same bytes the client hashes). Only when flow-s1.sh exits 0 (which happens only in effective `on` mode) and `answers.outcome.choice` is `none_ran` or `all_skipped`: `"output_check": {"verdict", "site": "quality.tests-ran", "model", "confidence"}`. Otherwise the entry is byte-for-byte the shape it had before.
- **Ledger reader**: `Run.passing` is `exit_code == 0 and not masked and not failed and output_check is None`. `output_check` is read only when it is an object whose `verdict` is one of the two values; anything else is ignored. `status` prints `LAST_RUN_OUTPUT_CHECK=none_ran|all_skipped` when the most recent run carries one.
- **Gate**: a new reason after the failed one: "the last quality run exited 0 but its output showed no tests ran" (or "... showed every test was skipped"). For a run with a null exit code, a reason that says the exit code is not known, names a timeout, a call in the background and a command shape as causes, and says a test command counts only when it runs in the foreground, finishes, and runs on its own, after nothing but `cd <dir> &&`, assignments or a leading `set` line, naming `env`, `time`, `nice` and `timeout` among the shapes that leave it unknown; a masked run with a null exit code says its exit code was masked without printing a number. The latest run's reason is given also when an earlier run passed ("last passing run at T; since then, <reason>"); without a passing run it ends "; no passing run this session". Exit codes and modes are unchanged.
- **Repository control**: a repository's settings can only lower the user's mode for the site (`on` > `shadow` > `off`); the hook reads the mode from `bin/flow-s1-mode.sh`, the one place that applies this rule, so a repository can neither start shadow nor switch the site on. `project` kinds are never asked, so a repository pattern such as `.` cannot widen what is sent.

### Risk map

| Area | Plausible wrong version | Discriminating check |
|---|---|---|
| State versus client shortening | Output sent as one string, or the head kept: the summary is cut away | 1,000-line output of 58-character lines, summary on the last line, trailing newline, `stateTokenCap` 3000, so the 200 tail lines alone are over the cap and the client must shorten every line: the stub's logged `output_tail` ends with the summary line. 1,000 lines rather than more because the test harness writes every payload into the artifact, and bash 3.2 takes over a minute on a payload of several hundred KB, longer than the stub runs |
| Pre-filter scope | Asks on lint, on `project` patterns, on masked or failed runs, or before the mode check | Zero-request scenarios: non-test command, `ruff check`, `pytest \|\| true`, interrupted pytest, repository pattern `.` with `uses=shadow`, site off with a provider, repository-only `on`, repository-only `shadow`, user `shadow` with repository `off` |
| Direction rule | An answer upgrades a failure, or `unclear` / shadow downgrades | Failing payload + stub `executed`: 0 requests, entry failed; shadow + `none_ran`: passing; on + `unclear`: passing |
| Off and no-answer identity | A stray field or a lost entry when off, provider none, timeout, http 500 | Ledger line compared with the line the hook at origin/main (85b63bc4) writes for the same payload, `at`, `s1_state_sha256` and `exit_code` removed; `exit_code` is checked on its own: null from that hook, 0 from this one |
| Call status versus the test's status | A failing run piped to tail, grep or tee, followed by `; echo`, `&& echo` or `\|\| echo`, put in the background, or after a heredoc is recorded as exit 0 and passes the gate, and its output is sent to the provider as a pass; or a plain run after `cd x &&`, `FOO=1` or a leading `set -euo pipefail` line is refused | Real-shape payloads with a failing summary in stdout for each refused shape: exit code null, no request, no passing run; `cd x && pytest`, `FOO=1 pytest`, `pytest -q 2>&1` and `set -euo pipefail` on its own line before `pytest` keep 0 and are asked about. | Reader backward compatibility | A malformed `output_check` downgrades or crashes the reader | Hand-written entries with `output_check` a string, an unknown verdict, null: status equals the same ledger without the field |

### Threshold

`outcome` default 0.9, provisional. It satisfies the stated constraints: only `none_ran`/`all_skipped` at or above it downgrade, it is high because a wrong downgrade blocks a real pass, and it takes effect only when a user switches the site on. No `models:` entry until the shadow comparison measures one for jev-1.13.0.

### Open, to confirm during shadow collection

Whether the hook's `tool_response` has the same keys as the transcript's tool result: the exit-code rule above rests on the transcript keys, and gives null for any key outside its list, so a difference costs a plain re-run, never a false pass. To check against a captured hook payload in the collection session.

Claude Code's hooks documentation (read 2026-10-01) does not say whether `tool_response.stdout` for Bash is shortened for long runs. The state takes the tail of what the hook receives; whether that is the runner's real tail is to be checked against a long run's transcript in the collection session.
