## Design Decision: Flow factory, labelled issue queue to ready PR
**Date**: 2026-11-12 | **Category**: architecture
**Decision**: A Python engine (bin/flow-factory.sh wrapping bin/_flow_factory.py) is the only writer of job state and runs a checked transition table (docs/flow-factory/transitions.json, 172 rows, checker and 98 fault-injection tests passing). Workers are claude -p processes per stage in per-job worktrees; intake and approver are tool-less judges. Two executors over one engine: a headless runner and /flow:factory run in a session, which asks blocking questions immediately while the worker waits. Phase 1 ends at a ready PR merged by a person; phase 2 adds opt-in auto-merge from the outside-session runner only.
**Options considered**: interactive-only orchestrator; headless-only runner; hybrid engine with both executors (chosen); stage work inside the session (rejected: loses per-stage limits and result equality).
**Trade-offs**: a large state table and a Python dependency on macOS; workers share the person's OS user and GitHub token.
**Rationale**: a deterministic engine with data-defined transitions can be checked mechanically; separate worker processes give per-stage budgets and the same result under both executors.
**Non-goals**: no merge without a person in phase 1; no OS-user isolation of workers; no reuse of zazen code (GPLv3, ideas only).
**Failure modes**: accepted risk that a worker or session running as the person can post, label, edit, close or merge with the keyring token, and can read raw comments; probes P1-P14 are go/no-go with fallbacks, and a stale probe group pauses launches.
**Consequences**: ordinary /flow:start, /flow:review and /flow:address stop when a factory job holds the same issue; tier-gate loads factory rules only where the factory is used; tiers.issueUpdate is a new Tier 2 key.
