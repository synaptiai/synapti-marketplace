# Flow factory design inputs

These files are the inputs to the flow factory design. The factory takes GitHub issues that carry a queue label and drives each one to a ready pull request without a person starting each step. The plan is in `plan.md`.

| File | What it holds |
|---|---|
| `plan.md` | The approved plan: decisions, design summary, probes, phases and verification |
| `design.json` | The full design, one section per key. `states_and_transitions` explains the state machine and points at `transitions.json`. `person_channels` says who may act for a person and how the engine checks it: from a terminal, by a trusted comment, or from a Claude session in default permission mode, where tier-gate's ask is the confirmation; in auto mode a session confirms nothing. `worker_github_access` sets out the two options for how workers reach GitHub. `phasing` holds the questions for the user and the phase 2 acceptance criteria. `__open_before_fix` lists the items that were open before an earlier revision |
| `design-check-2026-11-11.json` | An earlier check of `design.json`: which of the items open at that time its text closed, and the contradictions the check found |
| `design-check-open.json` | The 39 items a later check of `design.json` found, at commit e15b1950. The current `design.json` and `transitions.json` fix each one or record it: as a probe's go condition, as a phase 2 acceptance criterion, or as a question for the user in `phasing` |
| `design-critic.json` | The critic's findings on the first synthesized design |
| `gaps.md` | The 24 gaps between flow 3.16.0 and an unattended factory, each checked against flow's code |
| `research-zazen-factory-v2.md` | Analysis of the ZazenCodes software factory v2 (GPLv3: ideas only, no code or prompt text is reused) |
| `research-aidlc-v2.md` | Analysis of AWS AI-DLC v2 |
| `research-flow-lifecycle.md`, `research-flow-runtime.md` | How flow's commands, state and safety checks work today, read at aab0d132 |
| `transitions.json` | The job state machine as data: states, events, facts, fact dependencies and rows, each row with the blocking GitHub writes it makes. It also holds, as data, the rules the design states in prose (`rules`), the rows applied before every event of a pass (`pass_first`), and the outcome each of 47 situations must have (`expectations`). It is the only source for the state table |
| `check_transitions.py` | Checks `transitions.json`: schema and allowed keys, duplicate JSON keys, where each fact is defined, which states each event must occur in, guard coverage, precedence ties, rows that never win, resume targets, reachability from the creation row to a terminal state and to ready through winning rows (a park taken in a state never counts as a way into it), and exits from parked states into active states. Every rule, the event order, `pass_first` and the expectations are required, and the checker keeps its own list of the 47 expectation ids, so deleting one together with the rows it protects fails. It enforces: a person action needs its confirmation; a blocking write whose key is confirm parks first; a move out of a state where the PR is marked ready undoes the mark, only rows 41, 41e and 41k resume into such a state, and a confirm park taken there resumes into ready; every engine push is preceded by the protected check, and a violation freezes the job with nothing pushed; a person's merge wins over every other event of the same pass; and the stage outcomes, such as ready only with a gate record, a valid review and a passing ledger at the head. It prints the entry and exit lists. `--markdown` writes `transitions.md` |
| `transitions.md` | Generated from `transitions.json` by the checker. Not edited by hand |
| `test_check_transitions.sh` | Applies broken edits to a copy of `transitions.json`, at least one for each rule, each required key and each kind of expectation, and checks that the checker rejects each one with that rule's own message. It also checks that `transitions.md` matches the JSON and that every row id `design.json` cites exists. By default it runs under `/usr/bin/python3` (3.9) and `python3` |

`transitions.json` is the only source for the job state machine; `design.json` describes it and cites its row ids. If they disagree, `transitions.json` is correct. `design.json`'s `finding_closure` names the section that addresses each defect listed in `plan.md` Step 1. Two of them are closed only if the user adopts the machine-account rule for comments: the GitHub comment channel, and the comment path in the auto-mode defect. On this Mac, `gh auth token` prints the person's keyring write token even with GH_TOKEN and GITHUB_TOKEN unset (checked 2026-11-12), so neither worker token option closes the comment channel; only the machine-account rule, or a separate OS user for workers, does. Six questions remain for the user, listed in the `phasing` section of `design.json`: approve the sandbox repository; create the read-only token workers use (the design chooses that option, as the plan directs; without the token, workers get no credential); how to close the comment channel (the machine-account rule, a separate OS user for workers, or accepting the risk; if the user does not choose, the channel stays an open defect and phase 1 does not ship as closing it); re-intake on retry; whether workers reading untrusted text with gh is recorded as a departure from the plan or closed by a separate OS user; and whether to add a setting that drops cloud credentials from workers. The plan's decision table settles the rest.
