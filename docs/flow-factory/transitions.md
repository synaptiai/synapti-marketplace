# Flow factory job state machine

> Generated by `check_transitions.py --markdown` from `transitions.json`. Do not edit this file by hand; edit the JSON and run the checker again.

The single table of job states, events, guards and transitions. check_transitions.py validates it and derives the entry and exit lists; transitions.md is generated from it.

## How to read the table

- **precedence.** Within one (state, event), when several rows match, the row with the lowest precedence number applies. Ties are errors.
- **guard.** An object fact -> true/false. All listed facts must hold. A fact the guard omits is not read by that row.
- **stay.** A row with "stay": true leaves the job in its state and applies its effects.
- **computed_targets.** "to": "resume_state" or "blocked_stage" moves the job to the value a parking row recorded. "resume" lists the possible targets, and the checker compares it with the "records" of the rows in "resume_from" ("*" means every row entering the state that records the value).
- **no_move_ok.** An event's no_move_ok entry lets the job stay in the listed states when no row matches and the facts agree with "when". Each entry has a written reason.
- **event_order.** Within one engine pass, events are applied in event_order. A job that left its state ignores the later events of that pass, and a stage result for a stage it left is refused with that stage's lease. A change that a github_change reported stays pending until a row whose guard reads its fact as true has applied, and the sync raises github_change again in each later pass while a change is pending. So a change seen in the same pass as a move, or under a row with a lower precedence number, is applied in a later pass, in the job's new state. One exception comes before the order: when the sync of the pass shows the job's PR merged by a person (pr_merged_by_person), row 54 is applied first, so a cancel, reject or other person event of the same pass cannot end a merged job as cancelled or rejected.
- **slots.** A job takes a slot when a stage of it launches and it holds none; row 66w keeps the launch waiting while no slot is free. The job keeps the slot while it stays in active states other than queued and ready. The engine frees it whenever the job enters ready, a parked state or a terminal state, so rows do not repeat that effect. Rows 2 and 36 also read slot_free, so a job does not leave queued, or undo ready to go to sync, while no slot is free. Row 55 does not read it: approve keeps the PR marked ready, and the approver's launch waits for a slot at row 66w. Row 36u does not read it either: the undo of ready has already run, so the job goes to sync and its launch waits at row 66w.
- **ready_and_drafts.** A PR is marked ready only in ready, in the phase 2 states approve, merging and waiting_ci, and in waiting_operator while the job waits for the undo of ready (pending_undo_ready). Every move out of ready, approve, merging or waiting_ci to another non-terminal state first runs gh pr ready --undo and removes the flow:ready label, and such a row lists 'undo of ready' in its writes. That undo is a blocking write: when its key resolves to confirm, rows 40, 40f, 40g, 40j, 40l, 40p, 40r, 40t, 40x and 40y park the job in waiting_operator first, and row 40h holds every github_change there until the undo is confirmed or observed. After it, the job resumes into ready with the PR no longer marked, and the held event is replayed there. If the replay does not move the job, ready_mark_missing is true and row 36u sends it to sync at the next sync_tick, in the same pass or the next, and row 31 marks the PR ready again.
- **run_by.** Each active state names what runs it: the engine inline, an engine directive, a judge with no tools, or a claude -p worker. check_transitions.py requires launch_due, lease_expired and stage_failed in exactly the states run by a directive, judge or worker, stage_succeeded in those run by a directive or worker, worker_parked and question_stored in worker states, and github_change, person_cancel and person_rebuild in every non-terminal state.
- **writes.** A row's 'writes' lists the blocking GitHub writes it makes, per from-state where they differ. blocking_write_confirm is derived from them: it can be true only when the row that would win with it false lists a write, and then a row that parks in waiting_operator recording resume_state wins. The writes of a review, rework or resolve result are made before the result's row applies, so row 20b lists them too.
- **rules_and_expectations.** 'rules' and 'expectations' hold, as data, the rules the design states in prose. check_transitions.py fails when a row breaks one: for example when a person action acts without its confirmation, when a blocking write has no confirm park, or when a person's cancel, merge or rejection does not end the job.

## Rows

Rows are grouped by event. Within one state and event, the lowest precedence number applies.

Row 1 (creation, event issue_labelled) moves a new job to queued when: the issue is open and carries the queue label; the label actor has triage or higher; no non-terminal job exists for the issue; no terminal job has vouch_at at or after this label event; no open PR closing #N from a non-factory branch whose author has write access or higher (a fork PR from an outsider does not block); no flow:in-progress label without a local job. Effects: set vouch_at = the label event time; write job.json; no baseline_digest yet.

## Rules the checker enforces

- **Creation.** Every creation row targets queued, and reachability starts there.
- **Goal.** Every non-terminal state can reach ready through winning rows, not only end the job.
- **Person confirmation.** Every row on person_approve_spec, person_confirm, person_feedback, person_rework, person_retry, person_reject, person_cancel, person_rebuild reads unvouched_session_action. A row that reads it true stays and refuses, and no no_move_ok entry of those events lets a job stay while it is true. An always-ask person subcommand acts only with the confirmation the engine checks (design person_channels item 4); rows 69a to 69h refuse without it.
- **Blocking writes.** blocking_write_confirm is derived: it can be true only when the row that wins with it false lists a write (assignment, in-progress label, push, PR create or edit, review marker, resolution marker, replies, ready mark, undo of ready), and then a row that parks in waiting_operator recording resume_state must win. A blocking write whose tier key resolves to confirm waits as a pending intent in waiting_operator (design github_writes_and_tiers).
- **Ready mark.** A row that moves a job out of ready, approve, merging, waiting_ci to a non-terminal state outside them lists 'undo of ready', unless it is a confirm park or its guard reads ready_mark_missing true; a row that enters one of them from elsewhere lists 'ready mark'. conventions.ready_and_drafts.
- **Records as if.** Row 14 records resume_state, for each from-state, as the targets the rows winning with spec_approval_required false enter. After approval the job enters the state row 13 would have entered.
- **Records as if.** Row 20b records resume_state, for each from-state, as the targets the rows winning with spec_change_needs_approval false enter. After approval the job enters the state the stage's own row would have entered.
- **no_move_ok literals.** Every literal of a no_move_ok "when" is left open by the fact dependencies in each of its states.
