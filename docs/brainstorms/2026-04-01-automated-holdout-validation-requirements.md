# Automated Holdout Validation

## Problem Frame

Quality gates in the ai-first-org-design-kit have satisfaction targets (90%, 95%, 98%, 85%, 95%) but no empirical measurement. Holdout scenarios exist as documentation in `gates/.holdouts/` but are never programmatically tested against real agent output. The evolution-auditor estimates gate health from user interviews — recall-biased, manual, and infrequent.

Two inseparable problems:
1. **No gate telemetry** — can't answer "are we at 90% first-pass plan approval?"
2. **No anti-gaming verification** — agents might pass self-review by checking boxes without genuine understanding, and there's no way to detect this

The fix: a separate LLM-as-Judge evaluator that tests agent output against hidden holdout scenarios inline during gate self-review, producing both actionable feedback and telemetry data.

## User Flow

```
Executing Agent                          Holdout Evaluator (isolated)
     │                                          │
     ├─ Completes work                           │
     ├─ Runs /org-gate-review                    │
     │   ├─ Reads gate file (visible criteria)   │
     │   ├─ Self-reviews: criterion → evidence    │
     │   ├─ Produces self-review table           │
     │   │                                       │
     │   ├─ Spawns holdout-evaluator ──────────► │
     │   │   (passes: gate name + work output)   ├─ Reads holdout scenarios
     │   │                                       ├─ Evaluates output vs each scenario
     │   │                                       ├─ Maps failures to visible criteria
     │   │                                       ├─ Writes telemetry record
     │   ◄── Returns mapped feedback ────────────┤
     │   │                                       │
     │   ├─ Combines self-review + evaluator      │
     │   ├─ If all pass: "Gate passed"            │
     │   ├─ If fail: shows actionable feedback    │
     │       (references visible criteria only)   │
     │                                           │
     ├─ Fixes issues, re-runs if needed          │
     ├─ Presents to Daniel                       │
```

## Requirements

**Holdout Evaluator Skill**

- R1. New skill `holdout-evaluator` in `plugins/ai-first-org-design-kit/skills/` that evaluates agent output against holdout scenarios using LLM-as-Judge
- R2. Evaluator reads holdout scenarios from `gates/.holdouts/{gate-name}-holdouts.md` for the specified gate
- R3. Evaluator receives three inputs: gate name, the self-review evidence table (what the agent claims), and file paths to the actual work output (what actually exists). This dual-input lets the evaluator cross-reference claims against reality.
- R4. For each holdout scenario, evaluator produces a verdict: PASS (output would not exhibit this failure mode) or FAIL (output exhibits this failure mode)
- R5. Evaluator runs in an isolated context — the executing agent's conversation does not include holdout content

**Feedback Model**

- R6. Evaluator produces two output layers:
  - **Detailed layer** (for telemetry only): which specific holdout scenarios passed/failed, with reasoning
  - **Mapped layer** (for the executing agent): failures mapped back to visible gate criteria, without referencing holdout scenarios
- R7. Mapped feedback format: "Holdout evaluation: PASS/FAIL. [If FAIL: Your work shows weakness on criterion N (criterion description). Specific issue: (description derived from holdout finding without revealing the scenario).]"
- R8. The executing agent never sees holdout scenario names, descriptions, or the detailed evaluation layer

**Integration with Gate Review**

- R9. The `org-gate-review` skill template (generated by operationalize) gains a second phase that spawns holdout-evaluator after visible-criteria self-review
- R10. Combined gate result: PASS only when both self-review AND holdout evaluation pass. If either fails, report the combined result as FAIL with feedback from both layers
- R11. If holdout evaluation fails but self-review passed: this is the specific signal that the agent is checking boxes without genuine understanding — the feedback should direct attention to the weak criterion

**Gate Telemetry**

- R12. Each holdout evaluation writes a telemetry record to `$HOME/.ai-first-kit/projects/{slug}/evolution/gate-telemetry.jsonl` (append-only, one JSON object per line)
- R13. Telemetry record schema: `{ timestamp, gate_name, scenario_count, pass_count, fail_count, failed_scenarios: [scenario_id], self_review_result, overall_result }`
- R14. The evolution-auditor reads telemetry records to compute empirical satisfaction metrics instead of estimating from interviews
- R15. Telemetry data enables: rolling satisfaction rate per gate, false positive/escape rates, holdout scenario effectiveness (which scenarios actually catch failures), trend analysis over time

**Evaluator Prompt Design**

- R16. The evaluator prompt must instruct the judge to evaluate whether the OUTPUT exhibits the failure mode described in each holdout scenario — not whether the output explicitly addresses the scenario. (Terminology: each "holdout scenario" describes a specific "failure mode" an agent might exhibit; "evasion strategy" refers to the class of anti-patterns the scenarios collectively detect.)
- R17. The judge evaluates behavioral evidence: does the output show signs of the failure mode, not just whether the right words are present
- R18. The judge must be skeptical of claims without evidence — "I verified X" without showing proof should trigger failures on evidence-related holdout scenarios

## Success Criteria

- SC1. Running `/org-gate-review plan-readiness` on a plan with unresolved assumptions (holdout scenario 1) produces: self-review PASS (if agent didn't catch it) + holdout evaluation FAIL with feedback pointing to criterion 2
- SC2. Satisfaction metrics for each gate can be computed from telemetry data after 10+ evaluations
- SC3. The executing agent's conversation context never contains holdout scenario content at any point during the evaluation
- SC4. The evolution-auditor can replace interview-based estimation with telemetry-based measurement

## Scope Boundaries

- Not in scope: holdout secrecy enforcement via Claude Code hooks (separate work)
- Not in scope: gate pass artifacts / proof-of-passage (separate work)
- Not in scope: holdout rotation or refresh mechanism (separate work)
- Not in scope: deterministic/mechanical checks as an alternative to LLM-as-Judge (future optimization)
- Not in scope: changes to how holdout scenarios are authored (quality-gate-designer stays unchanged)

## Key Decisions

- **Inline evaluation over post-hoc**: catches gaming in real-time rather than after-the-fact, at the cost of added latency per gate review
- **LLM-as-Judge over deterministic**: covers all scenario types (mechanical and subjective) with a single approach; accept the circular risk (LLM judging LLM) mitigated by isolated context and different prompts
- **Actionable feedback over opaque verdict**: maps failures to visible criteria so agents can improve, accepting the small information leak about which criteria are weak — this leak doesn't reveal the holdout scenarios themselves
- **JSONL telemetry over structured DB**: append-only flat file is simplest, aligns with existing file-based artifact pattern, queryable with jq
- **Dual-input evaluation (evidence + files)**: evaluator receives both the self-review evidence table (agent's claims) and actual file paths (ground truth). Enables cross-referencing — catches "claims without evidence" holdout scenarios by comparing what the agent says it verified against what actually exists

## Dependencies / Assumptions

- The `org-gate-review` skill template is generated by `operationalize` — changes to the template require re-running operationalize for existing projects
- Claude Code's Agent tool supports spawning isolated sub-agents that don't share the parent's conversation context
- The evaluator needs to receive the work output somehow — either as text content or as a file path reference the evaluator can read
